# CityMate 并发与故障验证报告

验证日期：2026-10-20。

补充说明：本文是正确性与故障恢复实验，其中 HTTP 场景使用进程内 TestClient。2026-10-22 新增的真实 TCP 压测、持续队列观察与真实模型任务负载单独记录在 [压力测试与容量验证报告](压力测试与容量验证报告.md)，不能从本文的 25 用户数量推导 QPS。

## 结论

现有 31 项后端测试在 SQLite + fakeredis、真实 MySQL + Redis 两种环境均通过；新增 10 项真实服务并发与故障验证全部通过。在本次覆盖的条件下，没有发现超卖、重复成单、重复返还库存、消费者中断后无法恢复或预约超额批准的问题。

本次新增可重复运行的测试，没有修改生产业务逻辑。结果支持当前演示及求职项目的核心正确性说明，不代表已通过生产压力、高可用或灾难恢复验收。

## 环境与隔离

| 项目 | 本次配置 |
|---|---|
| 系统与运行时 | Windows、Python 3.12.14、pytest 8.3.4 |
| MySQL | Docker 中的 MySQL 5.7.44，端口 13306，InnoDB |
| Redis | Docker 中的 Redis 7.4.11，端口 16379 |
| 测试数据库 | `citymate_test`，与演示库 `citymate` 分离 |
| 测试 Redis | DB 15，每个用例独立随机 `test:{UUID}:` 前缀 |
| 并发请求 | 线程屏障同时放行；HTTP 场景经 FastAPI TestClient 调用真实鉴权及业务路由 |
| 消费者故障 | 测试创建的独立 Python 子进程；不停止演示消费者或数据库容器 |
| 模型 | 此次测试关闭外部模型调用 |

测试夹具拒绝数据库名不是 `citymate_test` 的外部数据库。每个用例创建测试表、导入演示种子与 25 位测试用户，结束后删除测试表及该用例的 Redis Key。**不要将测试数据库改为业务库，也不要并行运行多个共享 `citymate_test` 的测试任务。**

## 执行结果

| 批次 | 结果 | pytest 记录耗时 |
|---|---|---|
| 原有后端回归：SQLite + fakeredis | 31 通过 | 17.48 秒 |
| 原有后端回归：真实 MySQL + Redis | 31 通过 | 74.12 秒 |
| 新增真实服务并发与故障验证 | 10 通过 | 45.46 秒 |

真实服务两批合计覆盖 41 个用例。上述耗时包含测试初始化、建表与清理，不能据此计算业务 QPS。测试有一条 Starlette/AnyIO 的弃用提醒，不影响本次通过结果；依赖兼容性升级需单独验证。

### 并发验证

| 场景 | 操作 | 实际断言与结果 |
|---|---|---|
| 多用户抢购，重复 3 轮 | 每轮重建数据，25 个已登录用户同时请求 10 个名额 | 每轮 10 个 HTTP 202、15 个 409；10 个不同订单和用户；消费后 SQL 与 Redis 库存均为 0，订单均为 `ready` |
| 同一用户重复提交 | 25 个请求同时领取同一优惠 | 仅 1 次新受理，其余返回同一个订单 ID；Stream 只写入 1 条消息 |
| 重复订单消费 | 12 个线程同时处理同一订单消息，再让 Worker 重放 | SQL 仅 1 笔订单，SQL 与 Redis 库存均为 9 |
| 重复取消与投递 | 同一订单同时取消 12 次，4 个线程投递 Outbox | 库存仅恢复到 10；之后可重新领取，产生新订单，库存回到 9 |
| 预约容量竞争 | 12 个座位，两份各 8 人的待审核预约同时批准 | 仅 1 份批准，另一份返回容量不足；剩余 4 个座位 |

HTTP 抢购使用进程内 ASGI TestClient，验证了接口、Session、真实数据库事务和 Redis Lua 的组合；没有经过实际 TCP、Uvicorn 多进程或 Nginx，因此不是网络负载测试。

### 故障验证

| 场景 | 故障方式 | 实际断言与结果 |
|---|---|---|
| 取到消息但未执行订单事务 | 子进程取到 Stream 消息后到达检查点，父进程强制结束它 | 退出前 pending 为 1、SQL 订单为 0；新子进程接管后生成 1 笔订单，库存为 9，pending 清零 |
| SQL 已提交但尚未 XACK | 子进程提交订单后、返回确认前暂停，父进程强制结束它 | 退出前已有 1 笔 SQL 订单且 pending 为 1；新子进程重放后仍只有 1 笔订单，库存没有再次扣减，Outbox 投递完成 |
| 数据库事务中途失败 | 在实际 SQL 扣库存后、事务提交前注入异常 | SQL 库存回滚至 10、订单和 Outbox 均未落库；Redis 保留预扣及 pending，解除故障后重试成功，最终两侧库存均为 9 |
| Redis 执行成功但响应丢失 | 实际执行取消补偿 Lua 后，测试包装器抛出连接异常 | Redis 已补偿，SQL Outbox 仍未完成；重试投递不会重复返还库存，最终两侧库存均为 10、买家记录释放 |
| 数据库拒单 | 原有测试故意使 SQL 库存不足，再消费已预扣的消息 | 订单标记 `rejected`，释放 Redis 领取记录并补偿该次预扣；这是注入不一致状态后的局部补偿验证，不是 Redis 整体重建验证 |

子进程恢复测试将 `reclaim_ms` 设为 0，以快速验证接管逻辑。生产 Worker 的默认接管阈值为 30000 毫秒；本次没有测量其完整等待时间。事务失败与 Redis 响应丢失使用测试注入，没有关闭真实数据库服务或模拟真实断网。

## 复现方式

测试文件：[test_real_reliability.py](../backend/tests/test_real_reliability.py)。沿用 [conftest.py](../backend/tests/conftest.py) 中的隔离夹具。

前置条件：

1. Python 环境已安装 `backend/requirements-dev.txt`。
2. MySQL 和 Redis 正常运行，已创建 `citymate_test`（`utf8mb4`），测试账号有该库建表、删表和数据操作权限。
3. 没有其他任务正在使用该测试库；测试会清理其中的项目表。

在 `backend` 目录、使用项目 Python 环境执行。下面的账号和端口对应本项目本机演示配置；其他机器需换成自己的测试连接，不要填业务库地址。

```powershell
$env:CITYMATE_TEST_DATABASE_URL='mysql+pymysql://citymate:citymate-local-only@127.0.0.1:13306/citymate_test?charset=utf8mb4'
$env:CITYMATE_TEST_REDIS_URL='redis://127.0.0.1:16379/15'
$env:CITYMATE_MODEL_ENABLED='false'

# 新增的 10 项验证
python -m pytest -v tests/test_real_reliability.py --junitxml=logs/reliability.xml

# 全部 41 项后端测试；和上一条顺序执行，不要同时启动
python -m pytest -q --junitxml=logs/backend-real.xml
```

测试程序自行启动和结束测试子进程，不需要启动普通业务 Worker。未设置这两个真实服务连接变量时，新增的 10 项测试会跳过，不能把跳过视为验证通过。回到默认模拟环境前，在同一终端移除变量：

```powershell
Remove-Item Env:CITYMATE_TEST_DATABASE_URL -ErrorAction SilentlyContinue
Remove-Item Env:CITYMATE_TEST_REDIS_URL -ErrorAction SilentlyContinue
```

本机实际结果保存在 Git 忽略的 `backend/logs/verification-20261020-baseline.xml` 和 `backend/logs/verification-20261020-reliability.xml`；本文提供可提交的结果摘要。

## 尚未证明的能力

- 千人级、持续高负载下的吞吐量、P95/P99 延迟与资源占用。
- 实际网络中断、MySQL/Redis 服务重启、持久化恢复、磁盘满与整体数据丢失。
- Redis 主从切换、哨兵/Cluster、高可用部署，以及锁到期但持锁业务仍在运行的竞争。
- 所有可能的事务交错、多个 API/Worker 实例的长期运行表现。
- 真实短信、支付、退款和商户核销。

求职讲解可以引用本次具体规模和故障条件，例如“在真实 MySQL、Redis 上验证 25 用户争抢 10 个名额，并在消费者提交前后强制结束测试进程验证恢复”，不应扩大为“生产级高并发”“故障下零丢单”或“所有异常均已覆盖”。
