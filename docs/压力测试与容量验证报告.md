# CityMate 压力测试与容量验证报告

验证日期：2026-10-22。本文记录本机演示部署的有限负载实验，不代表线上用户规模或生产容量上限。

本轮完成 7 个业务阶段和 18 个真实模型任务。订单与库存核对通过，约 10 请求/秒的两分钟阶段运行正常；更高负载出现积压和一次连接异常。Agent 流程断言全部通过，但人工检查仍发现能力越界承诺和输出标签问题。结果不能表述为“高并发和回答质量全面验收通过”。

## 1 验证方法

入口为 [`backend/evals/run_load.py`](../backend/evals/run_load.py)。脚本启动独立 Uvicorn API 进程和独立订单 Worker，以真实 HTTP/TCP 调用接口，使用真实 MySQL 与 Redis；不使用进程内 TestClient 替代网络请求。测试数据与网站业务库隔离。

- API 一个进程、Worker 一个进程，Worker 保持项目的批次大小、接管阈值和每轮 0.2 秒间隔。SQLAlchemy 连接池沿用每进程默认的 5 个常驻连接、最多 10 个额外连接。
- 预建合成用户和 Session；计时包含鉴权、接口逻辑、数据库和 Redis 访问，不包含验证码发送、登录、建库及启动。初始化库存缓存在计时前完成。
- 数据集使用项目基础种子（4 家商户、4 张初始优惠券、28 个预约时段、2 个示例账号）及 5,000 个合成测试账号，再为 7 个业务阶段各建一张券。没有导入网站的全部扩充商户，也没有百万级历史数据。
- 业务请求使用闭环负载：每个请求槽位等上次请求结束后继续发送。记录客户端未完成请求峰值，以及服务端 ASGI 请求生命周期重叠峰值。后者包括等待 I/O 的时间，不表示这些请求都在同时使用 CPU。
- 服务端计数直到 ASGI 应用返回才结束，客户端可能已收到响应并发起下一次请求，因此服务端峰值可能略大于客户端槽位数；两者口径不能混用。各级测试顺序执行，历史订单与消息保留，后面的阶段面对更大的历史数据集。
- 100 个不同用户争抢 10 张券；同一用户发出 50 个请求检查幂等；随后以 1、10、25、50 个请求槽位逐级加压，每级目标 20 秒。各阶段使用不同优惠券，并等待上一阶段清空队列。
- 持续阶段目标 120 秒，5 个请求槽位，发起速率上限 10 请求/秒。每阶段最多 5,000 个请求；采样发现队列积压超过 1,000 条后停止发起请求，最多等待 180 秒处理完毕。触及保护阈值不算达到了原定持续时长。
- 每隔约 1 秒采样一次 Redis 消费组 lag、pending、未投递 Outbox 和订单状态。查询耗时会延长采样间隔；监测本身也占用数据库、Redis 和主机资源。短于采样间隔的峰值可能漏采。
- 队列积压为 **lag + pending**，不使用 Stream 总长度冒充积压；消息历史总长度用于检查是否重复入队。Outbox 单独统计。
- 订单完成条件为 SQL 和 Redis 状态都变为 `ready`。完成耗时是首次轮询观察到该状态的时间，属于上界，含采样误差，不是精确的提交时间，也不是前端轮询体验测量。
- 核对每个被受理订单 ID、所属用户、SQL 最终状态、唯一购买记录、消息数量、SQL/Redis 剩余库存及库存守恒，最后检查队列与 Outbox 均清空。

Agent 另行以 1、2、4 个并发任务测试，每级 6 个任务：2 次两轮商户偏好修改、2 次预约草稿加明确确认、2 次政策问答。使用当前配置的真实 `Qwen/Qwen3-32B` 云端 API 和默认本地词项政策检索；不是模拟模型。预约验证还会核对数据库归属、状态、人数、时段，以及确认步骤不调用模型。

任务完成率根据工具参数、业务状态、来源和关键事实检查计算，不等于完整自然语言回答准确率。每级只有 6 个任务，采用最近秩百分位，P95 等于样本最大值，不能用来估计稳定的生产尾延迟。脚本不额外重试聊天请求，模型 SDK 自身的重试仍然保留；仅凭应用返回的 503 无法确定服务商是否返回过 429。

## 2 环境与证据

硬件为 Intel Core i9-12900H，14 核 / 20 逻辑处理器，Windows 可见内存约 31.73 GiB；Docker 共享 20 CPU、约 15.49 GiB 内存，测试 MySQL/Redis 容器没有单独限制 CPU 或内存。负载生成器、API、Worker、数据库和其他演示服务共用本机，结果包含资源竞争和本机网络开销。

MySQL 镜像为 `mysql:5.7`，Redis 为 `redis:7-alpine`，Python 3.12.14。精确服务版本、执行时间、源文件 SHA-256、每次请求、每次采样和真实模型响应保存在 [原始报告 JSON](evaluations/load-20261022.json) 中；环境见 [环境记录](evaluations/load-environment-20261022.json)，新增脚本的隔离保护和百分位计算测试为 [2 项通过](evaluations/load-runner-regression-20261022.xml)。本次没有修改生产业务代码，没有重跑历史全部测试。

本轮计时使用 `time.monotonic()`；此 Windows/Python 环境的实现是 `GetTickCount64()`，分辨率 15.625 毫秒。因此表中的毫秒数是量化后的观测值，不具备亚毫秒精度；短请求的延迟应按约一个时钟刻度理解误差。

**源码版本边界：** 最终核对发现，工作区的 `citymate/app.py`、`citymate/knowledge.py`、`citymate/knowledge_server.py` 在本轮运行期间被更新，新增了政策分块及参数传递。测试 API 在启动时加载模块，未开启热重载，因此本轮 Agent 结果对应启动时的本地词项检索版本，不验证这次新增的分块逻辑。订单业务、Worker、模型助手及压测脚本的指纹仍与运行开始时一致。原始报告保留开始时指纹，[收尾校验记录](evaluations/load-postcheck-20261022.json) 保留变化后的指纹；指纹用于区分版本，不是完整源码快照。用当前工作区复跑应作为新一轮验证，不能直接沿用历史结论。

测试库名必须是新建的 `citymate_load_<12位小写十六进制>`；Redis 必须为本机 DB 15，并使用该次运行独有的 `load:{运行编号}:` 前缀。脚本拒绝非空数据库、已存在的运行前缀和已有的报告文件，不执行删库或清空 Redis。结束时只关闭自身启动的进程。测试库和测试前缀保留，便于核对。

## 3 执行结果

### 3.1 后端业务

实际服务版本为 MySQL 5.7.44、Redis 7.4.11；Redis `appendonly=yes`、`appendfsync=always`。保持原部署设置，没有为了提高压测数字降低持久化参数。

| 阶段 | 槽位上限 / 客户端峰值 / 服务端峰值 | 请求数 | 发送阶段耗时（秒） | 接口 QPS | 接口 P95（毫秒） | 非预期错误 |
|---|---:|---:|---:|---:|---:|---:|
| 100 用户争抢 10 张券 | 100 / 100 / 100 | 100 | 0.656 | 152.44 | 578 | 0 |
| 同一用户重复领取 | 50 / 50 / 50 | 50 | 0.422 | 118.48 | 390 | 0 |
| 阶梯 1 | 1 / 1 / 1 | 394 | 20.015 | 19.69 | 63 | 0 |
| 阶梯 10 | 10 / 10 / 12 | 1,226 | 16.891 | 72.58 | 172 | 0 |
| 阶梯 25 | 25 / 25 / 31 | 1,247 | 7.422 | 168.01 | 188 | 0 |
| 阶梯 50 | 50 / 50 / 56 | 1,147 | 20.578 | 55.74 | 2,703 | 1（0.087%） |
| 持续 120 秒，限速 10/s | 5 / 3 / 3 | 1,200 | 120.437 | 9.96 | 63 | 0 |

争抢阶段 10 次返回 202、90 次返回售罄 409；售罄是符合库存条件的业务拒绝，不是系统异常。重复领取阶段 50 次返回 202，但只有 1 个不同订单 ID，不能把这 50 次算作 50 笔成单。短暂突发的 QPS 不代表可持续吞吐。

阶梯 10、25 均因采样积压超过 1,000 条而提前停止，没有完成原定 20 秒。阶梯 50 的异常为客户端 `RemoteProtocolError`，原始记录索引 1019；服务端记录到 1,146 个请求，和最终受理订单数相同。这次没有保存足够的服务端连接诊断，不能进一步断言连接异常由某个组件引起，也不能把它忽略为成功。

| 阶段 | 新订单数 | 采样积压峰值 | 未投递 Outbox 峰值 | 停止请求后清空耗时（秒） | 订单完成观测 P95（秒） | 含清空时间的成单吞吐（笔/秒） |
|---|---:|---:|---:|---:|---:|---:|
| 争抢 | 10 | 0 | 3 | 1.47 | 2.08 | 4.71 |
| 重复领取 | 1 | 0 | 0 | 0.69 | 1.11 | 0.90 |
| 阶梯 1 | 394 | 135 | 23 | 9.80 | 10.50 | 13.22 |
| 阶梯 10 | 1,226 | 1,040 | 25 | 73.84 | 71.77 | 13.51 |
| 阶梯 25 | 1,247 | 1,139 | 25 | 80.22 | 75.28 | 14.23 |
| 阶梯 50 | 1,146 | 945 | 25 | 81.14 | 78.97 | 11.27 |
| 持续 120 秒 | 1,200 | 8 | 7 | 0.75 | 1.75 | 9.90 |

表中积压 0 只表示采样时没看到积压，不表示瞬间从未排队。成单吞吐包含排空和轮询观测时间，不能当作 Worker 内部纯处理速率。全部 7 个阶段的最终积压、pending 和未投递 Outbox 均为 0。

共发出 5,364 个请求，形成 5,224 笔不同的最终订单。每个阶段均通过受理 ID 与 SQL ID 集合一致、用户归属、唯一购买、最终 ready、消息只入队一次、无超卖、SQL/Redis 库存守恒及完成状态核对。这里的无丢单、无重复成单结论只针对本次已受理请求及合成数据。

**结论：** 约 10 请求/秒的两分钟阶段没有出现持续积压，接口响应和订单完成均有观测证据；更高入口速率下，异步成单明显跟不上，并发 50 时还出现连接错误和尾延迟上升。因此不能宣称本项目可长期稳定承受 168 QPS 的成单业务。下一步性能排查应定位消费者事务、Outbox 回写和持久化 I/O 的耗时；本次未做分段 CPU/I/O 剖析，尚不能确定各项贡献，也没有实施生产业务优化。

### 3.2 真实模型 Agent

| 任务并发上限 / 实测任务峰值 / 服务端 HTTP 峰值 | 任务流程检查 | HTTP 成功数 | 整组耗时（秒） | 任务 P50 / P95（秒） | HTTP 单轮 P95（秒） | 完成任务/分钟 |
|---|---:|---:|---:|---:|---:|---:|
| 1 / 1 / 1 | 6/6 | 12/12 | 213.41 | 35.06 / 62.69 | 33.39 | 1.69 |
| 2 / 2 / 2 | 6/6 | 12/12 | 128.44 | 36.91 / 87.91 | 71.13 | 2.80 |
| 4 / 4 / 4 | 6/6 | 12/12 | 80.75 | 55.73 / 72.88 | 48.86 | 4.46 |

共 18 个完整任务、36 次 HTTP 聊天请求。程序检查全部通过；6 次预约均生成正确归属、商户、时段和人数的草稿，明确确认后进入 `pending_review`，确认步骤模型调用数为 0。6 次偏好修改均使用咖啡类别和 5,000 分预算调用查询工具；6 次政策回答均返回预约规则来源和“15 分钟”关键事实。

应用记录模型调用共 54 次，服务商报告 Token 共 83,968（各级分别 29,511、27,607、26,850）。这不是账单核算；应用返回成功不证明 SDK 没有重试。所有 36 次应用响应均为 200，但本次未直接采集服务商 429 与 SDK 重试次数，**不能确认是否经历过限流，也没有验证服务商配额上限**。不可把后台领券 QPS 换算为 Agent 对话能力。

**人工复核发现：任务流程通过不等于回答质量全部通过。**

- 原始报告 `agent` 中并发 4、任务 `index=3` 的两轮推荐均建议用户补充位置或商圈，以便提供附近选项。当前助手没有距离筛选能力，这属于超出已实现能力的暗示或承诺；自动检查只核对类别、预算和工具调用，因此没有检出。
- 并发 2 的推荐任务 `index=0`、`index=3`，以及并发 4 的 `index=3`，输出了 `<shop>`、`<商户ID>`、`<s1>` 等标签。前端有 HTML 转义保护，本文没有重新做浏览器渲染测试，但这些输出不符合自然、整洁的展示要求。
- 政策样本中的草稿有效期、确认后待审核、批准后扣名额与当前演示规则一致。这只覆盖同一个预约有效期问题的重复测试，不覆盖全部政策、所有角色或恶意提示。

因此本次只能称为 **18/18 个预设任务的流程断言通过，回答质量仍存在问题**。后续应补充“普通推荐也不得主动承诺附近筛选”和“禁止泄漏内部展示标签”的回归用例，再修改输出约束并重测。本次保留失败样本，不用后续修正结果覆盖本轮记录。

### 3.3 可以引用的结果

> 在 i9-12900H 本机、单 API + 单 Worker、真实 MySQL 5.7/Redis 7 环境下，以约 10 请求/秒持续运行两分钟，共 1,200 次领券请求全部成功，接口 P95 约 63 毫秒；订单双端完成状态的轮询观测 P95 约 1.75 秒，最终库存一致、无超卖或重复成单。进一步逐级加压发现异步订单积压，并在 50 请求槽位时观测到一次连接异常。

这段只描述本次实测，不能改写成“支持 5,000 用户同时在线”“稳定支持 168 QPS 成单”或“生产环境零丢单”。Agent 可表述为“建立真实模型多轮任务评测，记录流程通过率、耗时和回答缺陷”，不能写成“回答准确率 100%”。

## 4 复现

1. 安装项目后端依赖和测试依赖，准备本机 MySQL、Redis。
2. 生成新的 12 位十六进制编号，创建对应的空数据库并授权测试账号。不要复用网站业务库或其他测试正在使用的数据库。
3. 在 `backend` 目录设置连接环境变量并执行。下面的账号密码是占位符，按自己的本机测试环境填写。

```powershell
$env:CITYMATE_LOAD_DATABASE_URL='mysql+pymysql://测试账号:测试密码@127.0.0.1:13306/citymate_load_012345abcdef?charset=utf8mb4'
$env:CITYMATE_LOAD_REDIS_URL='redis://127.0.0.1:16379/15'
python -m pytest tests/test_load_runner.py -q
python -u -m evals.run_load --live-agent --output logs/load-new-run.json
```

`--live-agent` 会调用本地配置的真实模型并产生服务商费用；省略该参数只运行后端业务测试。可使用 `--host-info 环境记录.json` 附加硬件和部署说明。报告路径必须尚不存在。默认参数就是本文记录的实验配置，缩短时长或改变并发后应视为不同实验。

`execution_complete` 仅表示实验流程执行到结束；必须另行检查每个阶段的 `integrity`、错误率、保护阈值、积压和 Agent 任务通过率。不能只凭进程退出码判断性能与质量全部合格。

## 5 边界

本次验证不覆盖公网、多机部署、浏览器渲染、长时间浸泡、真实短信或支付，以及大数据量下的索引和历史消息清理成本。只测试一个 API 和一个 Worker，不能推导水平扩容后的结果。并发请求数量、QPS、订单完成速度和真实用户数是不同指标。

收尾确认测试 API 端口关闭、测试 Worker 心跳已过期；原网站 API 返回健康、消费者在线，前端 HTTP 200。保留本次独立测试库和 Redis 前缀用于核对，没有删改网站业务库。

历史的 25 用户争抢和消费者故障恢复属于另一组正确性实验，详见 [并发与故障验证报告](并发与故障验证报告.md)；此次压测不替代这些故障测试。Chroma/MCP 在本次负载实验中未启用，其独立联调证据见 [知识检索联调报告](知识检索联调报告.md)。
