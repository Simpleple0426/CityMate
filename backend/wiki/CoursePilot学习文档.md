# CoursePilot 后端学习路线

目标是能够用转班案例讲清整个后端，并能从现象定位到代码。详细章节和源码索引见[后端架构与源码学习指南](后端架构与源码学习指南.md)，关键原始函数见[重点代码](重点代码.md)。

## 19 建议学习路径与练习

### 第一阶段 读通请求

阅读 `lifespan()`、`chat()`、`run()`，画出组件初始化与调用关系。练习解释 `user_id`、`conv_id`、`request_id` 的区别，并找到入口哪些数据来自客户端、哪些来自模型、哪些来自数据库。

### 第二阶段 读通工具

阅读四个角色、`education_tools()`、`_call_llm()`。练习跟踪 `get_enrollment` 从模型工具定义到实际 SQL 的路径，解释为什么模型不能提供他人的 user_id，以及为什么仍需要真实登录鉴权。

### 第三阶段 读通转班

阅读条件解析、候选建议、政策核验、`prepare()` 和 `submit()`。依次尝试零补费、老师偏好、老师硬性要求、修改预算、取消、模糊确认、重复完整确认、确认旧草稿。每步检查 slots、revision、草稿状态和申请数量。

### 第四阶段 读通增强能力

阅读 MCP 客户端和服务端、RAG 管理器、记忆与 Skills。练习指出查询改写的模型调用发生在哪一层，检索失败会返回什么，以及修改 Skill 后如何重载。

### 第五阶段 读通评测

选择一个真实评测 JSON 场景，对照每轮输入、回复、工具轨迹和状态快照，解释哪些检查通过、哪些措辞仍需人工审阅。记录失败项根因，区分规则解析、模型工具选择、数据库约束和依赖服务故障。

## 每个阶段的自测问题

| 阶段 | 应能回答 |
|---|---|
| 请求 | 用户、会话、请求三个 ID 各负责什么，哪些组件在启动时创建 |
| 路由 | 明确规则和三路融合怎样配合，旧任务和新话题如何区分 |
| 工具 | 模型如何选择函数，白名单如何生效，提交为何不是模型工具 |
| 需求 | 修改时间为什么保留预算，偏好与硬约束如何区分 |
| 政策 | 条款怎样决定查询字段，unknown 为什么不能判成符合 |
| 申请 | 需求版本与指纹怎样使草稿过期，重复确认为何不重复创建 |
| RAG | Function Calling 与 MCP 各在哪一段，模型与本地 handler 如何连接 |
| 评测 | 29/30 的单位是什么，full 范围是什么，Judge 是否参与这项判断 |

## 实践记录模板

每次练习记录用户消息、conv_id、request_id、主辅角色、tools_used、requirements.revision、草稿状态、申请数量与实际结果。先看程序状态，再看回复是否准确传达状态。

优先练习：零补费筛班、改时段保留预算、老师偏好变硬要求、取消条件、模糊确认、重复确认、旧草稿确认、免费资格缺目标、政策变更后提交。

## 20 面试讲解参考

### 20.1 一分钟介绍

CoursePilot 面向培训机构的课程咨询和教务办理。我把业务分为课程咨询、选课规划、教务办理和费用与权益四个角色，通过意图和当前任务状态选择主角色及辅助角色。模型通过白名单工具读取业务数据和知识库；转班要求、草稿和申请存入 SQLite。个人资格由结构化政策条款和报名事实联合核验，提交由完整确认口令触发，并重新检查需求版本、政策和费用。知识检索通过 MCP 接入，另有分层记忆、动态 Skills、工具轨迹与回归评测。当前完成的是演示申请闭环，真实模型一次 30 场景回归中 29 个通过程序检查。

### 20.2 常见追问与回答要点

**为什么要多 Agent？** 业务职责和工具权限不同，费用核验与教务办理可以分别提供信息，再由负责人推进。代价是额外调用和协作耗时；简单问题只用一个角色。没有做充分对照时，不声称多 Agent 必然优于单 Agent。

**为什么不用历史对话直接维护要求？** 历史可能压缩、缺失或被模型误读。任务要求需要结构化、带版本、可在提交时确定性验证。

**如何防止幻觉办理？** 用工具查事实，模型只能准备草稿，确认提交由业务处理器执行；准备和提交都复核，草稿展示由数据库状态生成。自然语言解释仍可能不准确，需要评测和人工检查。

**RAG 与政策规则为什么共存？** RAG 适合获取文本依据，确定性规则适合判断个人是否满足条件。知识相关性不能代替字段比较和事实完整性。

**MCP 在哪里？** 知识客户端通过官方 SDK 启动 stdio 服务、初始化、发现工具和 call_tool；业务数据库工具仍在本地执行。

**29/30 说明什么？** 一次真实模型全链路人工场景回归的程序检查通过情况，覆盖预设状态与工具行为；不能当作线上准确率、Judge 得分或统计显著性结论。

**下一步生产化做什么？** 补充真实鉴权和管理接口权限，将轨迹持久化，处理同会话并发与多进程状态，接入审批系统，完善名额与支付事务，扩充真实用户评测。回答时把这些作为后续工作，不写成已实现。
