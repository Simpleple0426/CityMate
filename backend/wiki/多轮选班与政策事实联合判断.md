# 多轮选班与政策事实联合判断

本次深化合并两个方向：多轮需求维护与方案选择，以及政策知识与业务事实联合判断。无需训练模型或构建训练集。

## 可以体验的对话

前端选择 Python，学员 ID 使用 `student_demo`，每个示例单独新建会话。

### 多轮选班

1. “帮我转到周日班，不想补钱，老师最好不变”。
2. “下午不行，只能晚上”。
3. “最多补两百元也可以”。
4. “帮我转到 PY-SUN-EVE”。
5. 按返回的草稿口令确认。

第一轮周日下午班符合硬性要求，即使老师不同也不会因偏好而被排除。第二轮没有完全匹配方案：晚班需要补200元，系统说明冲突并询问是否放宽费用，不能自行放宽。第三轮才允许晚班。第四轮依然通过原有模型工具循环生成草稿，第五轮通过确定性确认处理器提交。

支持“时间不限”“费用不限”“老师不限”撤销对应条件；“老师不能变”是硬性要求，“老师最好不变”是偏好。相互矛盾的费用表达先追问，不部分放宽旧条件。

### 个人免费转班资格

1. “我是否符合免费转班条件？”
2. “PY-SUN-PM”。
3. “PY-SUN-EVE”。

第一轮先从本人报名确定课程，再检索适用政策，按条款查询已付金额、课程、进度等事实。目标未知时必须回答信息不足。补充下午班后可判定符合演示免费规则；改成晚班后，价格条件不满足。资格咨询本身不会生成申请草稿。

## 算法与数据流

### 需求更新

`core/transfer_requirements.py` 解析当前消息中的显式约束增量，包含允许/排除日期、时段、费用上限、老师偏好和目标班级。更新按用户和会话隔离，SQLite 保存版本、原始表达和更新记录。规则未覆盖的自由表达仍依赖原模型对话，不能宣称已实现任意自然语言的稳定语义理解。

初版采用保守的规则解析，避免模型任意改写用户硬性要求。没有训练或微调。新话题中的政策咨询不会覆盖正在办理的选班条件。约束变更会使旧草稿失效；提交前还会重新检查条件与版本。

### 方案选择

`agents/transfer_advisor.py` 先用政策过滤不可办理的班级，再过滤全部硬性要求；剩余候选按老师偏好、费用、稳定班级ID排序。无解时列出被排除原因，并仅建议确实能产生可行候选的单条件放宽方案，不执行放宽。

多个候选时，根据候选在日期、时段上的分布计算熵，优先询问能区分更多候选的维度。当前是简单的信息量启发式，并未验证其对所有用户的最优性。

### 政策决定要查询哪些事实

`core/policy_evidence.py` 从 `data/demo_docs/transfer_policies.json` 检索 topic、课程和生效日期匹配的政策，优先课程专属政策。并存多个适用版本时返回未知，不按相似度随意选择。

每份政策同时保存可读条款、条款ID、版本、生效范围和已核验的结构化条件。系统从条件中提取事实依赖，再通过字段白名单查询数据库。比如新增 `source.remaining` 条款后，执行器才会查询剩余课时；无需把新查询硬编码到该问题的处理分支。

每次判断返回：适用政策、逐条 pass/fail/unknown、事实值、查询来源、缺失字段、查询计划和条款引用。审计结果保存在现有工具轨迹中，可通过工具轨迹接口查看。

这是一份**人工维护、结构化的政策知识索引**，与通用 Chroma RAG 并存。当前不自动将任意上传的 PDF/自然语言文档转成可执行规则，也不使用自由 Text-to-SQL。未知字段或操作符返回未知，不执行文档中的代码或 SQL。未来新增规则要先核验其结构化表达并注册必要的事实字段。

## 业务与兼容性

- 只使用原有演示条件：同课程、同进度、目标有名额；不补差价需目标价不高于已付金额。没有擅自加入“七天内”“首次转班”。
- 新增老师信息为演示数据：原班和晚班张老师，下午班李老师。
- 数据库增加独立表，不删除已有报名、申请或会话记录。旧版没有政策快照的草稿需要重新生成确认。
- 用户要求版本、政策指纹、班级事实、费用和老师要求都会影响提交校验。申请仍停留在待审核，不转班、不扣款。
- 已提交申请的同一口令仍幂等返回原结果。
- 当前身份仍是客户端传入的演示ID，不是生产级登录鉴权。

## 验证方式与范围

在 CoursePilot 目录运行：

```sh
python -m unittest discover -s tests -v
python -m evaluation.transfer_benchmark --output data/eval/transfer-strategies.json
```

策略对照仅包含6个人工编写的确定性回归案例：保持相同班级数据、解析器和筛选器，对比只使用最后一轮要求与持续维护要求。结果是2/6与6/6；它说明这几类回归问题被覆盖，不代表真实模型成功率，也不能作为大规模泛化指标。

真实模型后端 full 联调已有 30 场景 29/30 报告，覆盖 HTTP、Redis、Chroma、MCP 与隔离 SQLite，详见[真实模型评测](真实模型联调与评测.md)。该结果不同于六案例确定性策略对照，也不证明任意自然语言解析或线上泛化能力。
