# CoursePilot 后端技术亮点

各项能力围绕课程咨询到待审核申请的闭环展开。源码路径以 CoursePilot 为根。

## 6 意图识别

**源码位置：** `core/intent_recognizer.py` 的 `IntentCategory`、`IntentResult`、`recognize()`、`_vote()`、`_extract_entities()`、`_load_template_embeddings()`、`_embed_text()`；辅助规则在 `core/education_policy.py`。

### 6.1 明确规则优先

`recognize()` 先查询包含历史上下文的缓存。命中明确教务表达时，直接返回业务类别，使用 `explicit_business_rule` 标记来源，避免简单明确的问题必须等待模型推理。

未命中明确表达时，LLM 与 Embedding 并行执行，同时运行关键词模式匹配。默认融合权重是 LLM 0.7、Embedding 0.2、关键词 0.1。每一路向自己的类别贡献“权重 × 置信度”，取累计得分最高的类别。低于默认阈值 0.5 时返回 `OTHER`。

例如 LLM 和关键词都预测教务办理，则两者贡献累加到同一个类别；Embedding 若预测费用类别，其贡献单独计入费用类别。融合不是简单平均三个置信度。

### 6.2 失败与细化

LLM 识别失败时，可以使用有有效结果的 Embedding 或关键词。泛化类别得分不高而关键词命中特定类别时，代码有进一步细化逻辑。实体通过规则抽取，与意图分类是不同步骤。

远端向量不可用时存在本地字符 n-gram 向量回退。模板和待分类消息需要使用兼容的向量空间；不能拿远端模板向量与本地问题向量直接比较。

缓存是进程内字典，有容量限制和批量清理逻辑。虽然部分注释称为 LRU，代码未实现严格的访问顺序 LRU，不应在面试中直接宣传为严格 LRU 缓存。`learn()` 加入纠正样本并处理模板缓存，不是在线训练模型参数。

## 7 Agent 角色与路由

**源码位置：** `agents/agent_orchestrator.py` 的 `AgentProfile`、四类 `EducationAgent` 子类、`AgentOrchestrator.__init__()`、`_route_decision()`、`run_collaboration()` 和 `_best_agent()`。

### 7.1 角色契约

`AgentProfile` 定义角色任务、工作流程、输入输出契约、工具范围以及模型参数。四个角色复用执行基类，但系统指令和实际工具集合不同。

| 角色 | 负责的结果 | 业务工具 |
|---|---|---|
| 课程咨询 | 课程和通用政策解释 | `list_courses` |
| 选课规划 | 候选班级和比较依据 | `list_courses`、`get_enrollment`、`check_transfer`、`advise_transfer` |
| 教务办理 | 生成转班草稿和查询申请 | 上述工具及 `prepare_transfer`、`get_application_status`、`assess_free_transfer` |
| 费用与权益 | 课时、差价和免费资格 | `get_enrollment`、`check_transfer`、`advise_transfer`、`assess_free_transfer` |

各角色还获得共享的知识检索工具。实际权限来自 `get_tools()` 返回的字典；`AgentProfile.tool_scope` 主要表达角色契约，不能只看它判断运行时权限。

### 7.2 如何选择负责人

`_route_decision()` 综合明确表达、识别意图、活动转班任务、当前任务焦点和要求更新。用户补充“改成晚上”时可继续原任务，明确询问新课程政策时可切换话题，避免一直被旧任务锁定。

主角色为教务办理时，日期或筛选表达可以引入选课规划角色，费用表达可以引入费用与权益角色。结果保存为 `RoutingDecision`，包含负责人、辅助角色、原因和置信度。

### 7.3 当前协作顺序

`run_collaboration()` 顺序执行辅助角色，把它们的结果放入结构化上下文，再执行主角色。主角色统一回答，办理前重新核验。辅助结果包含自然语言 findings、成功状态及工具列表，不是所有角色都返回严格 JSON Schema 的业务报告。

默认池每类只有一个实例。`_best_agent()` 可以按表现选择同类型实例，但当前监控降权不会自动把费用工作改派给课程咨询，也没有证明已实现生产级水平扩容。

## 8 模型工具调用循环

**源码位置：** `agents/agent_orchestrator.py` 的 `BaseAgent.handle()`、`_call_llm()`、`_validate_tool_input()`、`_build_system_prompt()`；工具定义位于 `agents/tools.py` 的 `AgentToolSpec`、`make_tool()`，业务工具集合位于 `agents/education_tools.py`。

### 8.1 循环过程

`_call_llm()` 先组织背景、实体、角色输入契约与用户消息，再把角色可用工具转换为 Function Calling 定义。模型返回普通文本时结束；返回 `tool_calls` 时，后端读取工具名和 JSON 参数，查询白名单，校验参数并执行 handler。

执行结果以 `role=tool` 消息写回，同时保留匹配的 `tool_call_id`。下一轮模型根据结果继续选择工具或生成回答。循环最多八轮，超过上限抛出错误。

```python
# 学习用简化流程，实际实现见 BaseAgent._call_llm
for turn in range(8):
    response = await model(messages, tools)
    if not response.tool_calls:
        return response.text
    messages.append(response.assistant_message)
    for call in response.tool_calls:
        spec = whitelist[call.name]
        validate(spec, call.arguments)
        result = await execute(spec, request, call.arguments)
        messages.append(tool_message(call.id, result))
```

### 8.2 身份与参数边界

工具 handler 接收 `Request` 和参数字典。查询当前报名时使用 `req.user_id`，不接受模型自行填写另一个学员 ID。JSON Schema 限制字段，执行器也有运行时校验；白名单中不存在的工具会返回失败结果。

这是工具层防止模型擅自扩大操作范围的设计，但无法替代 HTTP 层真实鉴权，因为 `req.user_id` 本身仍来自客户端。

### 8.3 轨迹与并发

轨迹记录角色、工具名、输入、执行状态、业务结果状态、耗时和错误等。工具调用成功与业务符合资格是两个概念：工具可以正常返回“不符合资格”，调用本身仍是成功的。

`_execute()` 为每次请求创建 worker，避免多个会话共享 `_last_tools_used` 和 `_last_tool_traces` 等可变字段；统计对象仍共享。该处理减少轨迹串扰，不等于已经解决所有同会话并发和多进程一致性问题。

### 8.4 确定性执行分支

`_execute()` 在部分免费核验或要求更新场景直接调用 `assess_free_transfer` 或 `advise_transfer`，通过固定渲染函数生成回复，不进入模型工具循环。模型与规则混合执行是当前架构的实际特点。

教务角色成功生成草稿后，后端还会用数据库草稿生成规范回复，明确显示班级、差价、状态与确认口令，避免模型漏掉关键办理信息。

## 10 多轮要求与候选推荐

**源码位置：** `core/transfer_requirements.py` 的 `extract_updates()`、`apply_updates()`、`violations()`；`EducationStore.requirements()`、`update_requirements()`；`agents/transfer_advisor.py` 的 `advise()`、`render_advice()`。

### 10.1 支持的要求

`days`、`excluded_days` 保存允许与排除的日期；`periods`、`excluded_periods` 保存时段；`max_fee_cents` 保存补费上限；`same_teacher` 区分 `required` 与 `preferred`；`target_id` 保存指定班级。

`extract_updates()` 从用户原始消息识别明确支持的表达，并保留 evidence 文本。例如“老师必须不变”是硬性条件，“老师最好不变”是偏好。当前日期、时段和费用主要作为约束处理，并非所有字段都支持任意软偏好。

“改成晚上”覆盖旧时段，但不会删除未被用户修改的预算；“时间不限”清除日期与时段限制；“取消费用限制”清除预算条件。正负条件冲突时返回歧义，`apply_updates()` 不会部分更新并悄悄放宽原条件。

`update_requirements()` 比较更新前后状态，有变化才递增 revision，保存最近修改事件，并把待确认草稿置为过时。要求在会话入口由用户消息更新，不由模型工具参数直接改写。

### 10.2 筛选与排序

`advise()` 查询当前报名和同课程候选，逐个执行政策核验及 `violations()`。全部硬性要求满足后，先按同老师偏好得分排序，再按差价升序，最后用班级 ID 保持稳定顺序。

没有结果时，代码只提出确实能产生可行方案的单条件放宽建议，等待用户同意，不自动执行放宽。多个候选在日期或时段上不同，则计算这些维度的熵，优先询问区分度更高的维度。该追问机制是确定性候选分析，不是模型学习得到的策略。

### 10.3 贯穿示例

默认原班为 `PY-SAT-AM`，周六上午，张老师，已付 2000 元。用户要求周日且零补费时：周日上午班无名额；周日下午班同课程同进度、有名额且零补费；周日晚班需补 200 元。

若追加“老师最好不变”，下午班仍可作为候选，但不满足老师偏好；若改成“老师必须不变”，下午班被排除，晚班又违反零补费要求，系统应解释冲突。若用户明确接受最多补 200 元，则晚班可能满足新的要求。这里的“可能”还需通过当前数据和适用政策核验。

## 11 政策条款与事实联合核验

**源码位置：** `core/policy_evidence.py` 的 `PolicyEvidence.retrieve()`、`assess()`、`OPS`、`SOURCE_FIELDS`、`TARGET_FIELDS`；政策文件 `data/demo_docs/transfer_policies.json`；业务入口 `EducationStore.assess_free_transfer()`。

### 11.1 政策如何选取

`retrieve()` 根据 topic、课程和有效日期筛选政策。有课程专属政策时优先专属版本；没有适用政策或出现版本冲突时返回 unknown。选定政策后，规范化 JSON 并计算 SHA-256 指纹，用于后续变更检测。

### 11.2 事实如何查

`assess()` 先查询用户所属课程，确定政策；随后扫描条款的 `left`、`right_field` 或 `value`，收集所需事实字段。字段只允许落在已注册的 source 与 target 白名单中，操作符只允许使用 `eq`、`ne`、`gt`、`gte`、`lt`、`lte`。

```text
政策条款：目标价格不高于已付金额
  → 所需字段：target.price_cents 与 source.paid_cents
  → 查询当前目标班级价格与当前用户报名付款金额
  → 比较并生成 pass 或 fail
  → 保存字段来源、政策条款引用及查询计划
```

用户 ID 和班级 ID 作为参数传入 SQL；字段映射由注册白名单控制。当前没有任意 Text-to-SQL，也不执行文档里的 Python 或 SQL。

### 11.3 三态结论

每条检查返回 pass、fail 或 unknown；整体返回 eligible、ineligible 或 unknown。存在明确失败条款时整体不符合；没有失败但缺少事实时整体未知；条款全部通过才符合。

结果包括政策 ID、版本、指纹、逐条值、字段来源、缺失字段、查询计划和条款引用。不能把 unknown 写成符合，也不能把“检索到政策文本”当作“完成个人资格核验”。

### 11.4 与通用 RAG 的关系

ChromaDB RAG 用于自然语言知识查询和解释；结构化政策索引用于可执行条件核验。两个系统并存。通过知识上传接口加入文档不会自动新增可执行政策；新增核验条款需要人工维护结构化条件，并注册必要事实字段。

## 12 草稿与确认提交

**源码位置：** `EducationStore.prepare()`、`submit()`、`cancel()`、`invalidate_draft()`；编排器 `_business_control()`。

### 12.1 生成草稿

用户明确选择目标班级后，教务 Agent 可以调用 `prepare_transfer`。`prepare()` 重新查询报名、目标和费用，核验政策及当前要求，无歧义且满足条件才生成草稿。旧待确认草稿变为 superseded，新草稿变为 awaiting_confirmation，同时保存需求 revision 和政策 fingerprint。

准备草稿不创建待审核申请。模型获得的是草稿工具，没有提交工具。

### 12.2 确认提交

`_business_control()` 只接受完整匹配的 `确认提交 <12位小写十六进制草稿ID>`。用户只说“可以”“确认”“好的”时，会显示草稿或提示，不能直接提交。

`submit()` 在事务中依次检查草稿是否属于当前用户与会话、是否已有申请、是否仍待确认，再重新核验源班、目标、费用、需求版本和政策指纹。任何关键变化都使旧草稿失效，要求重新生成并确认。

```text
awaiting_confirmation
  ├─ 用户取消 → cancelled
  ├─ 新草稿或要求变更 → superseded
  ├─ 提交时发现数据变化 → invalidated
  └─ 明确确认且复核通过 → submitted → application.pending_review
```

### 12.3 幂等与事务分别解决什么

幂等防止重复确认创建重复申请：`applications.draft_id` 有唯一约束，提交前先查已存在申请并返回它。事务让同一次提交的校验与状态更新保持一致。

事务不会保证未来审批时仍有名额。本演示不扣减名额、不改变报名，后续真实审批还需要重新校验并完成资源分配。因此不能把这里称为完整名额锁定或支付事务系统。

## 13 RAG 与 MCP 链路

**源码位置：** `agents/tools.py` 的 `build_shared_rag_tools()`；`integrations/tool_manager.py` 的 `MCPToolManager.call()`、`search_with_rewrite()`、`rewrite_query()`、`_rerank()`；`knowledge_backend.py`、`knowledge_client.py`、`knowledge_server.py`、`knowledge_base.py`。

### 13.1 Function Calling 与 MCP 的区别

Function Calling 是模型向应用表达要调用哪个函数及其参数；MCP 是应用与工具服务之间的协议。当前模型看到的是 `search_knowledge_base`，应用内部通过工具管理器调用 `knowledge_search`，再由 MCP 客户端与知识子进程通信。

工具管理器类名包含 MCP，不代表其中所有工具都跨 MCP。实际协议由 `ClientSession`、`stdio_client()` 与 `FastMCP` 实现；业务 SQLite 工具仍是本地 Python handler。

### 13.2 MCP 连接

`open_knowledge_backend()` 默认选择 mcp，也支持显式配置 local；MCP 出错不会偷偷切成 local。`connect_knowledge()` 启动当前 Python 的知识服务子进程，执行 initialize 与 list_tools，核验 `knowledge_search`、`knowledge_stats`、`knowledge_add` 是否存在。

客户端检查错误标志、文本块数量及 JSON 结果结构。子进程只转发必要运行环境与 Chroma 配置，不需要主模型密钥。服务端标准输出留给协议，日志写到标准错误。

`knowledge_add` 是管理接口用的 MCP 工具，不作为聊天 Agent 共享工具暴露。

### 13.3 检索增强过程

工具管理器改写查询，使用多个查询并行召回，合并去重后由 LLM 重排取 Top-K。ChromaDB 中的文档按句号和换行切分，默认块大小目标为 500 字符；它是简单切分策略，没有实现复杂文档结构解析或标准的重叠窗口方案。

不要写成已实现混合 BM25 召回、Cross-Encoder 重排或 PDF 自动政策编译，这些不是当前实现。

### 13.4 缓存与故障处理

`knowledge_search` 注册了 300 秒 TTL 缓存；工具管理器用进程内字典保存结果。知识工具执行受超时控制，连续失败可打开熔断器，冷却后进入半开状态探测，成功后恢复。

fallback 明确表达知识库暂时不可用，没有提供有效政策依据。业务确认不能凭这样的降级文本声称资格通过。缓存、熔断和超时主要作用于知识工具管理层，不是所有 SQLite 业务工具都统一经过同一层。

## 14 分层记忆

**源码位置：** `memory/conversation_memory.py` 的 `MemoryContext`、`MemoryManager.add_message()`、`get_context()`、`_compress()`、`_search_episodic()`、`update_profile()`。

工作记忆存在 Redis，保存近期消息并设置 24 小时 TTL。当前常量包含工作记忆上限 20、压缩阈值 15、压缩后保留近期 5 条。具体触发逻辑应对照 `add_message()` 和 `_compress()`，不能把阈值当作保证的上下文长度。

情景记忆使用 ChromaDB 的 `education_episodic` collection，保存历史片段和摘要并支持检索；用户画像使用 `education_user_profile`，保存提炼的偏好与实体。`get_context()` 将工作消息、摘要、历史命中和画像组合成模型上下文。

ChromaDB 优先连接独立服务，不可用时可以回退本地持久化实例；这与 MCP transport 的显式选择是不同层的机制。

`chat()` 返回前写回用户和助手消息，画像通过后台任务更新。画像用于个性化，不应替代当前任务的硬性要求；当画像与最新明确要求冲突时，办理应以持久化任务状态和业务事实校验为准。

## 15 动态 Skills

**源码位置：** `core/skill_loader.py` 的 `Skill.matches()`、`SkillManager.load()`、`reload()`、`prompt_for()`、`_load_resources()`；`BaseAgent._build_system_prompt()`；资源在 `skills/`。

Skill 是任务说明、参考资料、工具依赖和输出模板的组合。匹配依据是角色和关键词，可配合资源清单按需加入 reference 或 template。提示词有总字符预算，资源路径必须位于 Skill 目录内，资源不可用时提示缺失而不猜测。

`prompt_for()` 会考虑实际可用工具及资源匹配，避免把没有相应工具支持的流程无条件注入。超出预算时可退回入口说明，避免切断完整流程或模板。

`POST /skills/reload` 支持运行中重新读取文件。这里是显式重载，不是文件修改后必然自动监听更新。Skill 资源只作为上下文，不执行脚本，也不授予工具权限。

面试时可以用一句话区分三者：角色指令定义职责，Skills 提供按需业务流程，工具白名单限定实际可执行操作。

## 16 监控与工具轨迹

**源码位置：** `monitor/performance_monitor.py` 的 `PerformanceMonitor._collect()`、`_routing_penalty()` 和 `AnomalyDetector`；编排器 `get_stats()`、`update_routing_penalties()`、`_record_tool_trace()`。

监控周期读取 Agent 与工具统计，关注成功率、平均耗时、连续失败和熔断状态，执行阈值与异常检测，并提供 Prometheus 指标及可配置 webhook。实例评分综合成功率、延迟与 monitor_penalty。

当前默认每类只有一个实例，所以降权机制的作用不能包装为已经完成跨角色自动容灾。成功率主要来自执行层状态，不代表每个自然语言回答都正确。

`GET /trace/tool/{request_id}` 查询单次工具轨迹，`GET /trace/tools` 查询近期轨迹。轨迹保存在进程内有界队列中，默认容量来自配置，重启后消失，不是完整持久审计系统。未来生产化可落库并增加脱敏、访问控制和追踪关联。

## 17 评测与现有结果

### 17.1 三种验证不要混为一谈

**意图与质量评测：** `evaluation/evaluator.py` 的 `IntentEvaluator`、`LLMJudge`、`EndToEndEvaluator`，提供准确率、Macro-F1、回复评分及基线回归。Macro-F1 是各类别 F1 的平均，可减少大类别掩盖小类别效果的问题；Judge 评分是模型评价，不是数据库事实核验。

**真实模型业务回归：** `evaluation/live_eval.py`、`live_cases.py`、`live_report.py`，逐轮保存回复、工具轨迹和数据库快照，以预设程序检查判定场景是否通过。

**确定性策略对照：** `evaluation/transfer_benchmark.py`，六个人工案例对比只看最后一轮要求与维护多轮要求。2/6 与 6/6 仅支持这些案例的策略效果，不代表真实模型泛化能力。

### 17.2 core 与 full

core 包含真实模型、意图识别、Skills、业务工具与隔离 SQLite，使用脚本提供历史，不包含 Redis、MCP、RAG 和 HTTP。full 通过进程内 ASGI 调用实际 `/chat` 和 lifespan，连接独立 Redis、本地 Chroma 与 MCP 子进程。不包含浏览器操作、真实审批或支付。

### 17.3 已保存的证据

`data/eval/live-full-30.md` 和对应 JSON 记录模型 `deepseek-ai/DeepSeek-V4-Flash` 的一次 full 回归：30 个人工场景，29 个通过预设程序检查。失败项为口语预算条件；修复后的单独三次复测为 3/3，没有重新完整跑出的 30/30 证据。

该轮记录 109 次聊天请求、13 次远端向量请求；服务端返回 182949 tokens；每轮 P50 为 1532 ms，P95 为 21500 ms。包含快速规则分支与后台用量口径，不能当作纯模型生成延迟或直接推算生产成本。

`data/eval/live-evaluation-summary.md` 汇总这些结果与限制；Skills 五场景小样本对照为启用 5/5、关闭 4/5，不支持“稳定提升 20%”。此次完整回归也未证明长会话压缩效果或真实流量下的可靠性。
